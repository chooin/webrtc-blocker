WebRTC 逃逸测试

本页面探测顶层 window、两种前缀别名、三种 iframe 逃逸路径与 getUserMedia 是否已被 WebRTC Blocker 拦截。 默认状态下（未把本站加入白名单），前五行 RTC 探测应全部显示 已拦截；其中任何一行显示 未拦截 都是漏洞。 最后一行 getUserMedia 是例外，它默认就应该显示 未拦截，读法见下方说明。

对照基线：在未安装扩展的浏览器里打开本页面， 下面每一行都应该显示 未拦截——这是本页面作为验收工具的对照基线。 如果某一行在未安装扩展时就已经显示 已拦截， 说明这一行已经失去判别力，不能据它判断扩展是否生效。
已知存在这种情况的一行是「webkit 前缀别名」：如果当前浏览器版本已经不再提供 window.webkitRTCPeerConnection 这个历史别名，该行会一直显示 「已拦截（构造函数不可用）」，这与扩展无关，请以其余几行为准。
部分探测项可能显示 无法判定：代表页面自身无法确认结果 （例如 data: 文档未能在超时时间内回传消息），既不代表已拦截也不代表未拦截，请手动进一步排查， 不要当作「已拦截」计入结论。
怎么读 getUserMedia 这一行： 摄像头与麦克风的拦截由扩展里单独的「同时拦截摄像头与麦克风」开关控制， 而这个开关默认是关闭的。所以在默认设置下这一行显示 未拦截 是正确的，不是漏洞—— 只有打开那个开关并刷新本页之后，它才应该变成 已拦截。
而且这一行只有在本页通过 http://localhost 打开时才有判别力。 navigator.mediaDevices 只存在于安全上下文，用 file:// 或非 localhost 的 http:// 打开本页时它是 undefined， 这一行会无条件显示「已拦截（方法不可用）」——那与扩展是否生效毫无关系。 README 里给的 python3 -m http.server 8765 -d test-pages 加 http://localhost:8765/escape.html 正是为此。
